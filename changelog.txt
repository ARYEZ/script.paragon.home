2.43.0 (Aryez - 2026)
    Added: Move files. Four numbered directory slots per Kodi box, paired by
        number, so slot 1 here and slot 1 on the office box are the two ends
        of one copy. Under "Move files..." on the main menu.
    The job is pushing a folder to the boxes in the house -- a new
        skin.paragon to three of them -- without scp-ing it three times. So
        one row sends a slot to one box, and another sends it to every box
        that has that slot set, asked once and naming each.
    Menus rather than a two-pane window. A pane on each side is what you
        need when you are hunting for a folder; with four numbered slots
        there is nothing to hunt for, so the whole job is which slot and to
        which box. That also keeps it working under any skin.

        source does not are listed afterwards, and removing them is a
        separate yes. A mirror that deletes as it walks is one wrong
        direction away from destroying the destination, and on a screen
        showing two boxes the direction is the easy thing to misread -- so
        the confirmation spells FROM and TO out in words rather than drawing
        an arrow, and names the destination twice.

        the full path is only ever rebuilt from the two. A slot able to hold
        ".." would let a recursive overwrite reach anything on the box.

        which would grow as it walked and never finish; a tree deeper than
        24 folders, since Kodi cannot report a symlink and a loop is
        otherwise indistinguishable from a deep tree; and one over 20,000
        files, so a slot pointed at the root by accident stops.
    Slots are not copied down to satellites, unlike scenes and the palette.
        A slot says where files live on this box, so the box you are
        standing at is the one whose slots you want to set -- and it is
        usually a satellite, because the master is the one in the cabinet.
    Everything goes through Kodi's virtual filesystem, so a destination can
        be smb://box/share/... as easily as a local folder.

2.41.0 (Aryez - 2026)

        feels switched off. It reads "Quiet", and "Louder" once it is down.

        Kodi remote comes back rather than sitting silently at a new level.

        one number there is a better fix than a new version.

v2.33.0
- A satellite is a complete copy of the master now, not almost one.
- Learned infrared codes travel down with everything else. They never did,
  and they should have from the start: a sequence step that fires a code
  failed flatly on a satellite that had never learned it, and a satellite
  cannot learn one for itself. Half a copy is a sequence that works in one
  room and not the next.
- A satellite no longer searches for devices. Discovery invents entries, and
  the master decides which devices the house has -- a satellite that found one
  for itself would be listing something the master had not approved, until the
  next copy deleted it again. The Refresh devices row is replaced by Copy from
  the master now, and start-up discovery is skipped whatever the setting says.
- Learning and deleting an infrared code are refused on a satellite, and the
  blaster's menu offers neither. Firing one is untouched.
- Fixed: a Tuya key arriving in a copy reached the session but not the driver
  that needed it, so a plug whose key had just been copied down stayed
  unusable until Kodi was restarted. The drivers are handed those dictionaries
  when the hub is built, and the copy was replacing them rather than refilling
  them. Learned codes would have had the same fault the moment they started
  being copied.

v2.32.0
- A satellite can no longer edit anything the master owns. It never should
  have been able to: the devices, scenes, sequences, palette and Tuya keys are
  copied down from the master at start-up and every few minutes, and that copy
  is a plain overwrite. Anything built on a satellite was deleted within the
  sync interval, silently, with nothing anywhere saying why.
- What that covered: new and edited sequences, new and edited scenes,
  capturing a scene from the lights, renaming a device, disabling one,
  forgetting one, editing the colour palette, and typing in a Tuya key. All of
  it looked like it worked.
- The rule is enforced on the session now rather than in the menus, so nothing
  can write a shared file on a satellite whichever way it is reached. The
  menus then stop offering what cannot be done, so you are not shown a door

  the point of a satellite and it still is.
- Device discovery still writes on a satellite. devices.json is also where a
  refresh records what it found and at which address -- a cache rather than a
  choice -- and refusing it would leave a satellite unable to reach the very

v2.8.2
- Fixed "'ascii' codec can't decode byte 0xcc in position 0" when switching a
  later Kasa plug. A Python 2 trap, and the ordinary case rather than an edge
  one: a device address read back from devices.json is unicode, because that
  is what json.load produces on Python 2. That made the request URL unicode,
  which made the Host header unicode, and Python 2's httplib joins the headers

  was implicitly decoded as ascii and failed on its first random byte.

  str type. The same latent fault was in the Govee cloud client and is fixed
  there too, before it had a chance to surface.

  this machine's own addresses, which on a box with a VPN, a container bridge
  or an unhelpful hostname is a confident wrong answer -- and sweeping the
  wrong /24 looks exactly like sweeping the right one and finding nothing.
- The range now comes from every device already known to be on the network:
  one the search has just found, and anything already in the device list,
  whatever its brand. A Govee bulb's address states which subnet the house is

- The Kasa diagnostic now reports what the search did rather than only what it
  found: how many each pass turned up, which subnet was swept and how many
  hosts that covered, and which addresses it went out from. Reporting only the
  devices could not tell "the sweep ran and they are not there" apart from
  "the sweep never ran", which need opposite responses.

v2.7.1
- Fixed a Kasa search finding only some of the plugs. Two causes, one mine.
- Mine: the search sent from a socket it closed immediately afterwards. A Kasa
  device answers to the port the request came from, so every reply to those
  sends was discarded, and only the devices that happened to answer the one
  send from the socket that stayed open were ever found.
- Not mine: broadcast traffic. Mesh access points and guest networks routinely
  drop or fail to flood it, which reaches some devices and not others. After
  broadcasting, the search now addresses every host on the subnet directly,
  which does not depend on broadcast working at all. The Kasa app broadcasts
  too, so it can show fewer devices than this does for the same reason.
- When the sweep turns up devices the broadcast missed, the search says so.
  Silently working around a network fault would hide it.
- The broadcast now goes out three times rather than once. UDP has no
  retransmission, and several devices answering at once is exactly when one
  goes missing.
- A search stops as soon as everything has gone quiet instead of sitting out
  its whole window, so finding everything is usually about a second.

v2.4.0
- Tuya protocol 3.4 is now driven, which is what the GHome WP9 speaks. 3.4 is
  a different protocol wearing the same version number: it negotiates a
  session key on every connection, signs each packet with HMAC-SHA256 rather
  than a CRC32, renumbers both verbs, and moves the version header inside the
  encryption instead of in front of it.
- A wrong key on 3.4 is caught at the handshake, where the HMAC gives a
  definite answer, rather than several steps later as a reply that will not
  decrypt.
- Not every 3.4 reply carries a return code and nothing in the header says
  which do. Every payload is AES-ECB ciphertext, so the reading that leaves a
  whole number of blocks is the right one -- a check against the format
  rather than a guess between two options.
- 3.5 is still not driven: it encrypts with AES-GCM, which is a different
  cipher rather than a bigger version number. A 3.5 plug is discovered,
  listed, and says which version it speaks.

v2.1.2
- Supports the newer Broadlink data payload layout. RM4-family devices and
  later "RM Mini 3" units prefix the payload with a two byte length; RM2 and
  RM3-era hardware, including the RM Pro, does not. Only the older layout was
  implemented, so a newer device authenticated perfectly and then refused
  every command with error -5.
- The layout is guessed from the device type code and then corrected by
  experience: a command that fails is retried the other way, and whichever
  works is remembered for the rest of the session. Hardware sold as "RM Mini
  3" spans both generations, so the type code alone cannot be trusted.
- A command that fails both ways reports the original error rather than
  whatever the speculative retry produced, and does not flip the setting.

v1.7.1
